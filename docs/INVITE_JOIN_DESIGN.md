# Slice 8A Design — Real Household Invite / Join

**Design only. Nothing in this document has been implemented, migrated,
applied to Supabase, or committed.** It complements
`docs/MEMBER_INTEGRATION.md` (which explicitly listed "invitation email
delivery, invite acceptance, profile linking" as out of scope for that
slice — this is where that gets designed) and
`docs/PAYMENT_PERSISTENCE_DESIGN.md` (the same design-then-implement
split, applied here).

## 1. Audit — current flow, traced exactly

**"Invite by link" tab in `AddMemberDialog.tsx` today:**

```
Members page → "Invite" button → AddMemberDialog opens on the "Invite link" tab
  → a hardcoded constant: const INVITE_LINK = 'grocerymate.app/join/flat-4b'
  → "Copy" writes that literal string to the clipboard
  → nothing renders it as a clickable link, nothing resolves it —
    there is no /join/:token route in the app at all today
  → visiting that URL, even if typed in by hand, hits App.tsx's catch-all
    (`<Route path="*" element={<Navigate to="/groceries" replace />} />`)
    and silently redirects into the app, doing nothing
```

**Every fake/non-functional part, precisely:**
1. `INVITE_LINK` is a single hardcoded string, identical for every
   household on earth — not household-specific, not a real token, not
   generated by anything.
2. There is no backing route, page, or Supabase object it could resolve
   to even if it were real.
3. The word "flat-4b" is a leftover from `src/store/household.ts`'s
   decorative `mockHousehold` — confirmed unrelated to the signed-in
   user's real household (already flagged and partially fixed for
   *display text* in Slice 5/6's truth audits; the link itself was left
   as a known, documented, non-functional limitation at the time).

**The same dialog's "or send it for them" email field is a *second*,
different, also-broken mechanism** — worth separating clearly from
"Invite by link" because it's easy to conflate the two:
- `AddMemberDialog`'s `handleInvite` → `useMembers.handleInvite` →
  `useHouseholdMembers.inviteMember(name, email)` performs a **real**
  Supabase INSERT: a genuine `household_members` row with
  `status='invited'`, `invited_email` set, `profile_id=null`, a display
  name derived from the email's local part.
- No email is ever sent (no email system exists — confirmed, and
  explicitly out of scope for this slice too).
- No accept flow exists anywhere that could ever set that row's
  `profile_id` and flip its `status` to `'active'`.
- `HouseholdProvider.loadHousehold` queries `household_members` filtered
  by `.eq('profile_id', profileId)` — an unlinked `profile_id=null` row
  **can never be found by anyone's session**, confirmed by reading the
  query directly. Every such row created today is permanently orphaned.

Both are real product gaps; only the second one silently writes real,
unrecoverable rows to the database, which is worse than doing nothing.

**Supporting architecture already in place, traced directly:**
- `household_members.status` already includes `'invited'` with
  `invited_email`, `invited_at` columns (Migration 1) — designed with a
  *different* model in mind (a pre-named placeholder waiting to be
  claimed by a matching email), not the link/token model this document
  designs. Not reused here — see §5, §12.
- `create_household()` (Migration 3) is the only precedent for "a
  SECURITY DEFINER RPC that atomically does a sensitive, identity-
  deriving, multi-row write, deriving the actor from `auth.uid()` and
  never trusting client-supplied identity." The invite-accept RPC in
  this design follows the exact same shape.
- `household_members_household_profile_key` — a partial unique index on
  `(household_id, profile_id) WHERE profile_id IS NOT NULL` — already
  guarantees one profile can't hold two membership rows in the *same*
  household. It does **not** guard against a profile belonging to two
  *different* households — see §6's redirect design for why that matters.
- `HouseholdContext.HouseholdStatus` already has an `'unsupported'` state
  ("More than one active... membership — no switcher yet, so refuse to
  guess"), rendered by `HouseholdGate.UnsupportedHouseholdScreen`. This
  is the exact dead end a poorly-designed accept flow could walk a user
  into — confirmed reachable today only in theory, never actually
  triggered by any current code path.
- `HouseholdGate` never *navigates* — it renders an in-place replacement
  screen keyed on `status`, and is only reached *inside*
  `<ProtectedRoute>`, itself only reached for any path that isn't `/`,
  `/sign-in`, or `/sign-up` (`App.tsx`'s manual pathname branching, not a
  nested `<Routes>`). A new `/join/:token` route needs its own top-level
  branch, sitting *outside* `HouseholdGate` — a brand-new user accepting
  an invite has `status: 'needs-setup'` and must not be shown "Create
  your household" instead of the join page.
- `AuthProvider.signUp()` calls `supabase.auth.signUp()` with no
  `emailRedirectTo` at all today — after hosted Supabase's required email
  confirmation, a new user lands wherever the project's default Site URL
  points, with zero memory of anything. `GuestRoute`/`SignInPage`/
  `SignUpPage` all navigate to a hardcoded `/groceries` on success; there
  is no "return to where I was going" mechanism anywhere in this codebase
  today, for any feature.
- `household_members_insert_owner`'s RLS policy requires
  `private.is_household_owner(household_id)` — the accepting user is by
  definition not that, so a plain client-side INSERT could never satisfy
  it. Acceptance structurally requires a SECURITY DEFINER RPC (§7).

## 2. MVP user journey

```
Owner (on Members page)
  → "Invite" → real invite generated server-side, real token in a real URL
  → copies the URL (still just a copy-to-clipboard button — no email/SMS sending)
  → sends it however they like (WhatsApp, Messenger, anything) — outside the app
Recipient
  → opens the URL → GET /join/:token
  → sees "You're invited to join <household name>" (name only — see §3)
  → not signed in yet → "Sign up" / "Sign in" buttons, invite preserved (§6)
  → completes signup (incl. hosted email confirmation) or login
  → lands back on the SAME /join/:token, now authenticated
  → sees the same invitation card, now with "Accept & join"
  → accepts → one atomic server-side transaction (§8) creates their real
    household_members row
  → redirected into the app → household loads for real, they can add/see
    groceries, settlements, etc. normally, as an ordinary member
```

No email-sending system is designed or required — the owner is the one
who transmits the link, exactly like sharing any other link.

## 3. Invitation model — `household_invites`

| Field | Type | Why it exists | Required? |
|---|---|---|---|
| `id` | uuid | Row identity. | Required |
| `household_id` | uuid | Which household this invite grants access to — the single source of truth the accept RPC uses; never supplied by the accepting client (§7). | Required |
| `token_hash` | text | The invite's secret, **hashed** — never the raw token (see below). What `resolve`/`accept` look up by. | Required |
| `created_by_member_id` | uuid | Who generated it — same anti-impersonation anchor pattern as `grocery_items.created_by_member_id`/the payment design's `created_by_member_id`, derived server-side, never trusted from the client. | Required |
| `created_at` | timestamptz | When it was generated. | Required |
| `expires_at` | timestamptz | A leaked or forgotten link should stop working eventually without anyone having to remember to revoke it — see §4/§10 for the 7-day default. | Required |
| `revoked_at` | timestamptz, nullable | Lets an owner kill a link early (sent to the wrong chat, no longer needed). Null = still live. | Optional (null by default) |
| `accepted_at` | timestamptz, nullable | Marks a single-use invite as spent — see §4. Null = not yet used. | Optional (null until accepted) |
| `accepted_by_profile_id` | uuid, nullable | Who actually used it — an audit trail ("who joined through this specific link"), and the field the atomic accept transaction conditionally sets (§8) to make double-acceptance structurally impossible. | Optional |

**Rejected fields:**
- **A raw token column.** Never stored — see below.
- **`role`.** Would let an invite grant something other than "regular
  member" — not a real MVP need, and a way to accidentally build a
  role-escalation surface. Hardcoded `'member'` in the accept RPC instead
  (§9).
- **`max_uses`/`use_count`.** Only meaningful for a reusable-link model;
  not needed once §4 recommends single-use.
- **`note`/`label`** (e.g., "invite for Sam"). A nice-to-have for an
  owner managing several pending invites, not required to make the
  *flow* work. Deferred, not because it's risky, just because it isn't
  necessary for MVP.

**Token strategy:**
- Generated **server-side**, inside the `create_household_invite` RPC —
  same "keep the sensitive logic in one place, server-side" precedent as
  `create_household()`. Cryptographically random, high entropy (32 bytes
  / 256 bits — e.g. `encode(gen_random_bytes(32), 'hex')`, a 64-character
  hex string, safe to put directly in a URL path with no escaping).
  256 bits makes guessing computationally meaningless regardless of any
  rate limiting (§10) — the entropy itself is the defense.
- **Only the hash is stored** (`token_hash`), computed server-side at
  creation time. This requires the `pgcrypto` extension (`digest(token,
  'sha256')`) — not currently enabled anywhere in this project (confirmed:
  no migration references it; `gen_random_uuid()` is used precisely
  because it's built into core Postgres and needs no extension). Enabling
  `pgcrypto` is a one-line, standard, Supabase-supported
  `create extension if not exists pgcrypto;` in Migration 8B — noted here
  as a real, small, new dependency, not silently assumed.
- A fast, uniform hash (SHA-256) is appropriate here — unlike a password
  (low entropy, needs slow hashing like bcrypt to resist brute force), an
  invite token already has 256 bits of entropy, so a fast hash used only
  for exact-match lookup is the right tool, not a weaker choice.
- **The raw token is returned to the owner exactly once** (the
  `create_household_invite` RPC's return value, used to build the
  `/join/:token` URL shown/copied in the dialog) and is never persisted
  anywhere in plaintext, including logs — matching the same
  "never store the secret" instinct already applied to Supabase API keys
  throughout this project's own hosted-verification work.
- **Resolving** a token (§7) hashes the incoming raw token the same way
  and looks up by `token_hash` — the raw value is never compared directly
  against anything stored.

**No leakage before validation:** `resolve_household_invite(token)` is
designed to return *only* `household_name` and a validity status — never
the member list, never other members' emails, never any financial data,
never anything about a *different* household (§7/§10).

## 4. Single-use vs. reusable — recommendation: **single-use (A)**

| Consideration | Single-use | Reusable |
|---|---|---|
| Roommate UX (3 people, 1 link) | Owner clicks "Generate invite" once per person — trivial repeat action | One link, multiple joins — nicer for a group-chat share, but not required |
| Accidental forwarding | Harmless once naturally consumed by the intended person; a second recipient just sees "already used" | A forwarded link stays a standing open door until someone notices and revokes it |
| Revocation | Same mechanism either way, but the *cost* of forgetting to revoke is small (one link, one potential extra join, and only until it's first used) | The cost of forgetting to revoke is unbounded — every day it's live, more strangers could join |
| Abuse | Contained automatically — leaking it publicly grants at most one uninvited join | Leaking it publicly (e.g. posted in a public channel) could let an unlimited number of strangers join a private household before anyone notices |
| Implementation complexity | One boolean-ish check (`accepted_at is null`) | Needs a real policy decision (unlimited vs. capped uses) — more design surface for no MVP benefit |
| Beta speed | "Generate invite" is a repeatable one-click action; no meaningfully slower onboarding | Marginally more convenient for the exact "3 people click the same link" case, not required to onboard fast |

**Recommendation: single-use.** The "generate invite" action itself is
kept fully repeatable (the owner can click it as many times as they have
people to invite — nothing in this design limits a household to one
invite ever), so single-use costs almost nothing in onboarding speed
while meaningfully containing the worst-case blast radius of a leaked or
accidentally-forwarded link. A future "pending invites" list (see
non-invites in the owner's own tab, letting them see/revoke outstanding
links) is a natural, small follow-up, not required for 8C.

**Expiration default: 7 days**, fixed for MVP (no owner-configurable
expiry UI — that's more control surface than beta needs). Long enough for
a real recipient to get around to clicking a WhatsApp link; short enough
to bound a forgotten/leaked link's live window.

## 5. Existing non-account members — recommendation: **always create a new row (A); defer claiming**

GroceryMate already supports `household_members` rows with
`profile_id = null` (added via "Add member" — a roommate with no
account, a real financial participant with real historical grocery
references). The question: when that same real person later gets an
account and joins via an invite link, should acceptance create a
brand-new row, or link/"claim" their existing one (preserving their
grocery history under one stable identity instead of splitting it across
two)?

**Recommendation: always create a new row for MVP. Explicitly defer
claiming.**

Claiming is a genuinely valuable *future* feature (preserving financial
history when a non-account member "graduates" to a real account) — but
every safe way to do it requires information this slice's link-based
invite doesn't have:

- **Name matching is explicitly ruled out** (by the task, and
  independently: two different real people can share a display name in
  this app by design — Slice 3/5's own duplicate-name handling exists
  *because* that's allowed — so name matching would be a real
  wrong-person-claiming risk, not a hypothetical one).
- **Email matching isn't available either**, for a different reason:
  this slice's link-based invite doesn't collect or require an email at
  invite-creation time at all (the owner just generates a link, without
  saying in advance who will use it) — there is no `invited_email` to
  match against, unlike the *old*, separate email-invite mechanism (§1),
  which does have one but is a different feature this design doesn't
  reuse.
- Any *safe* version of claiming would need the **owner** — not the
  invitee, and not an automatic string match — to explicitly pick which
  existing placeholder member a specific invite is "for," at
  invite-creation time (a `target_member_id` on the invite, a member
  picker in the invite UI, and accept-time logic that claims that
  specific row instead of inserting a new one). That's real additional
  surface (UI, RPC branching, a new failure mode if the owner picks
  wrong) that isn't justified just to onboard beta users quickly.

Every accepted invite in this design therefore always inserts a **new**
`household_members` row — full stop; no matching, no claiming, no
name/email heuristics of any kind (§9).

## 6. Auth redirection

**Do not rely on component state that dies across a full page
navigation or a different tab** (the task's own instruction) — hosted
Supabase's required email-confirmation step is exactly that: the user
leaves the app entirely, may open the confirmation link in a new tab or
even a different device, and lands back with no shared JS runtime state
at all.

**Design — two complementary mechanisms, not one fragile one:**

1. **The token lives in the URL itself** (`/join/:token`), which is
   already durable across a reload in the *same* tab.
2. **A `localStorage` breadcrumb**, written the moment `/join/:token` is
   first visited (regardless of auth state):
   `localStorage.setItem('groceryMate.pendingInviteToken', token)`.
   This is the mechanism that survives the actual worst case — a brand
   new user who signs up, closes the tab, opens their email client
   (possibly in a different tab or even a different device entirely if
   they're not careful, though this specific breadcrumb only survives
   *same-browser* continuations, which covers the realistic common case
   of "confirm on the same phone/laptop they signed up on"), and clicks
   the confirmation link. `localStorage` — not `sessionStorage`, not
   React state — is the only thing guaranteed to still be there.
3. On *any* transition into `signed-in` (a fresh sign-in, a fresh
   sign-up that got an immediate session, or the app's own normal
   session-restore on load), a small check — not inside `ProtectedRoute`/
   `HouseholdGate` themselves, but a thin wrapper that runs once, before
   they would otherwise redirect to `/groceries` — looks for the
   breadcrumb; if present, redirects to `/join/<token>` instead of the
   default destination, then clears the breadcrumb once the invite page
   reaches a *terminal* outcome (accepted, or a definitive rejection like
   expired/revoked/invalid/already-a-member-elsewhere) — not on a
   transient network error, so a real retry is still possible.
4. **Nice-to-have, not required:** `signUp()` could additionally pass
   `options: { emailRedirectTo: `${origin}/join/${token}` }` so the
   confirmation email itself lands the user directly back on the right
   page, skipping the breadcrumb round-trip for that one case. This
   depends on the project's Supabase Auth "Redirect URLs" allow-list
   already covering the app's own origin (commonly true, since the app
   already redirects successfully post-confirmation today, but not
   something this design assumes without checking at 8B/8C
   implementation time — and not a Supabase *configuration* change this
   document is proposing, since passing `emailRedirectTo` is an
   application-code parameter, not a dashboard setting). The
   `localStorage` breadcrumb is the mechanism this design actually
   depends on; this is a pure optimization on top.

**Other states `/join/:token` must handle, all server-derived (§7),
never guessed client-side:**
- **Already authenticated, opening a fresh invite** → skip straight to
  the invitation card with "Accept & join."
- **Expired / revoked / invalid token** → distinct, honest messages (not
  a generic "something went wrong") — see §11.
- **Already accepted** (this exact single-use token was already
  consumed, by this user or another) → "This invite has already been
  used."
- **Already a member of *this* household** (signed in, and their own
  active membership is already for the household this invite points to)
  → "You're already part of this household," with a link into the app,
  not an error.
- **Belongs to a *different* household already** — the case that would
  otherwise walk them into `HouseholdGate`'s existing
  `'unsupported'`/two-memberships dead end. The accept RPC itself refuses
  this server-side (§7/§8), and the page shows the same kind of honest,
  already-established messaging `UnsupportedHouseholdScreen` uses today
  ("GroceryMate doesn't support multiple households yet"), not a raw
  database error.

## 7. Authorization

| Action | Who | Enforcement |
|---|---|---|
| Create an invite | Household **owner** only | RLS: `private.is_household_owner(household_id)` on the `household_invites` INSERT policy — same pattern as `households_update_owner`. Owner-only is explicitly acceptable for MVP per the task. |
| Read/resolve an invite by token | **Anyone**, including signed-out visitors | A SECURITY DEFINER RPC (`resolve_household_invite`), deliberately grantable to `anon` too — the one narrow, intentional exception to "anon has no access" anywhere in this schema, scoped to return only `household_name` + validity (§3/§10). Not a raw SELECT/RLS policy — a caller with no membership can't be granted table-level SELECT no matter how it's scoped, and doesn't need to be. |
| Accept an invite | Any **authenticated** user | A SECURITY DEFINER RPC (`accept_household_invite`) — required, not optional, since the resulting INSERT could never satisfy `household_members_insert_owner`'s owner-only check from the invitee's own session. Derives identity exclusively from `auth.uid()`; the only client input is the opaque token (§8). |
| Revoke an invite | Household **owner** only | RLS: same owner check, as an UPDATE policy (`revoked_at`) — or, more simply, a small `revoke_household_invite(invite_id)` RPC that re-derives `is_household_owner` itself, for the same "never trust a bare column-level UPDATE grant to carry the whole authorization burden" reasoning `grocery_items` already established. |

**What the client can never choose, for `accept_household_invite`:**
`household_id` (derived from the token, not a parameter at all),
`role` (hardcoded `'member'` in the function body), `profile_id`
(always `auth.uid()`), and *which* member row is affected (always a
fresh insert, never an update to an arbitrary existing row — §5). The
function's only parameter is the token.

## 8. Join transaction

One PL/pgSQL function body = one implicit transaction, the exact same
property `create_household()` already relies on:

```
accept_household_invite(p_token text) returns table(household_id uuid, member_id uuid)
security definer, search_path pinned, executable by authenticated only:

1. v_caller := auth.uid()  -- raise if null (defense in depth; anon is already revoked at the grant level)
2. look up household_invites by token_hash = hash(p_token)
   -- not found            → raise "Invalid invite."
3. revoked_at is not null  → raise "This invite has been revoked."
4. expires_at <= now()     → raise "This invite has expired."
5. accepted_at is not null → raise "This invite has already been used."
6. exists an active household_members row for v_caller (ANY household)
                           → raise "You already belong to a household."
   -- this is the check that keeps HouseholdContext's 'unsupported'
   -- state (>1 active membership) structurally unreachable through
   -- this RPC — see §1/§6.
7. UPDATE household_invites
     SET accepted_at = now(), accepted_by_profile_id = v_caller
     WHERE id = v_invite_id AND accepted_at IS NULL
     -- the WHERE clause is the concurrency guarantee (§10): Postgres's
     -- normal row lock on UPDATE serializes any concurrent acceptance
     -- attempt; whichever transaction commits first "wins" the row,
     -- and the second one's UPDATE affects 0 rows once it proceeds.
   IF 0 rows updated → raise "This invite has already been used."
     -- re-check after the lock, not just before it (step 5 alone is a
     -- race without this — see §10 double-click/concurrent-acceptance)
8. INSERT INTO household_members (household_id, profile_id, display_name, role, status, joined_at)
     VALUES (invite.household_id, v_caller, <caller's own profiles.display_name>, 'member', 'active', now())
     RETURNING id INTO v_member_id
9. RETURN (invite.household_id, v_member_id)
```

Because steps 7–8 happen inside the same function call, either both
commit or neither does: a failure inserting the membership (e.g. a
constraint violation) rolls back the invite's `accepted_at` update too,
so a real failure never permanently burns a single-use invite for
nothing — exactly the task's own stated requirement.

## 9. Role / status result

An invited user who successfully accepts always ends up with:

- **`role: 'member'`** — never `'owner'`. Hardcoded in the RPC body, not
  derived from anything about the invite or the caller. A household's
  owner is only ever set once, at `create_household()` time (Migration
  3's `household_members_one_owner_per_household` partial unique index
  also structurally prevents a second owner row from ever existing,
  independent of this RPC).
- **`status: 'active'`** — not `'invited'`. By the time this row is
  created, the person has already authenticated *and* explicitly
  accepted; there's no meaningful intermediate state left to represent.
  (Contrast with the old email-invite mechanism's `'invited'` rows, which
  represent a *pre*-acceptance placeholder — a different model, not
  reused here — see §1/§5/§12.)
- **`profile_id`**: the caller's own `auth.uid()`, always — never null,
  never anyone else's id.

## 10. Security / abuse

| Threat | Mitigation |
|---|---|
| Token guessing | 256 bits of entropy — computationally meaningless to brute-force at any request rate; no rate limiting is required to make this safe (though ordinary API rate limiting, if the platform already provides it, is a free bonus, not something this design needs to add). |
| Token leakage (posted somewhere public, forwarded to the wrong person) | Single-use (§4) bounds the damage to at most one uninvited join; owner-initiated revocation (§7) closes it immediately once noticed; a 7-day expiry (§4) is the backstop if no one notices at all. |
| Expired / revoked token | Checked identically by both `resolve` and `accept`, each with its own distinct, honest error message (§6/§11) — never a generic failure. |
| Replay (reusing an already-consumed token) | `accepted_at IS NOT NULL` check, both at initial validation and — critically — re-checked inside the same atomic UPDATE that consumes it (§8), closing the gap a check-then-act race would otherwise leave open. |
| Double-click / concurrent acceptance | The conditional `UPDATE ... WHERE accepted_at IS NULL` in §8 is the actual guarantee: Postgres's row lock means only one concurrent call can ever see 0-rows-not-yet-updated and proceed to step 8's INSERT; every other concurrent or later call — same user double-clicking, two tabs, a network retry — deterministically gets "already used," never a duplicate membership row. |
| Cross-household manipulation | The accept RPC takes only a token; `household_id` is derived entirely server-side from the invite it resolves to, never a client parameter — there is no field for a client to substitute a different household into. |
| Role escalation | `role` is hardcoded `'member'` in the RPC body — not derived from the invite, not a parameter, not influenced by anything client-supplied. |
| Profile impersonation | `profile_id` is always `auth.uid()` — the RPC has no parameter that could name a different profile. |
| Enumerating households via invite endpoints | `resolve_household_invite` only ever responds to a syntactically-plausible, correctly-hashed 256-bit token; there is no "list invites" or "list households" surface, and a wrong/malformed token gets the exact same "Invalid invite" response as any other lookup miss — no information is leaked by trying. |

Deliberately **not** built for MVP (over-engineering for this stage):
IP-based rate limiting, CAPTCHAs, invite-creation quotas, audit logging
beyond `accepted_by_profile_id`/`created_by_member_id`, or any kind of
"suspicious activity" detection.

## 11. Routes / UI

**One new route: `/join/:token`.** Sits at the same top level as
Landing/`/sign-in`/`/sign-up` in `App.tsx`'s existing pathname branching
(§1) — reachable whether or not the visitor is signed in, and never
passed through `HouseholdGate`. Reuses existing components
(`AuthLayout`, `Button`, `Card`, spinners, the same visual language as
`SignInPage`/`HouseholdOnboardingPage`) — no new visual design.

States the page renders (one at a time, driven entirely by server
responses, never guessed client-side):

| State | What's shown |
|---|---|
| Loading | Spinner while `resolve_household_invite` runs |
| Valid, signed out | "You're invited to join **{household_name}**" + Sign up / Sign in buttons (§6 carries the token through) |
| Valid, signed in, not yet a member anywhere | Same invitation card + "Accept & join" |
| Accepting | Button shows a submitting state; disabled against double-click (§10) |
| Accepted | Brief success state, then into the app (`/groceries`), with `household.refresh()` triggered so the new membership is picked up immediately |
| Expired | "This invite has expired." |
| Revoked | "This invite is no longer valid." (Deliberately the same user-facing wording as expired is *not* required — a distinct message is fine and arguably more honest, but need not reveal *why* it was revoked.) |
| Invalid | "This invite link isn't valid." (also covers malformed/garbage tokens) |
| Already accepted | "This invite has already been used." |
| Already a member of this household | "You're already part of **{household_name}**." + a link into the app |
| Belongs to a different household (unsupported) | The existing `UnsupportedHouseholdScreen` messaging pattern — "GroceryMate doesn't support multiple households yet" + sign-out |

## 12. Existing "Add member" UX — the distinction, and what to remove later

**Preserve, unambiguously, two different actions in the Members
dialog:**
- **"New member"** (existing "Add member" tab, unchanged) = a real
  financial participant with no account — still exactly what it is
  today.
- **"Invite link"** (this design) = a real, working, single-use link
  that turns into a real authenticated household member with their own
  login, once implemented.

**Once 8C is actually built** (not now — this document doesn't touch
any code), the "Invite link" tab's content should be replaced entirely:
the fake `INVITE_LINK` constant and its copy button are replaced by a
real "Generate invite" action calling `create_household_invite`, showing
the real returned URL. The **"or send it for them" email sub-section
should be removed at the same time**, not kept alongside the new real
link — leaving both would mean two differently-broken/differently-real
"invite" mechanisms living in the same tab (one a working link, one a
dead-end placeholder-row generator with no way to ever complete), which
is confusing rather than clarifying. This is a deletion/simplification
of existing UI, not a redesign, consistent with the task's own
instruction to eventually "remove the existing fake... behavior."

## 13. Test plan

**RLS / RPC (SQL, `SET ROLE` + `request.jwt.claims`, the same technique
already established for every prior slice's adversarial regression):**
- Owner creates an invite; a regular (non-owner) member cannot; `anon`
  cannot.
- `resolve_household_invite` works for a signed-out (`anon`) caller and
  returns only `household_name` + validity — never member/financial data.
- Successful acceptance: real `household_members` row created, correct
  `household_id`, `role='member'`, `status='active'`, `profile_id`
  matching the caller, never the owner's role.
- Refresh persistence: after accepting, a page reload shows the household
  as normal (no session-only state involved anywhere in this design).
- Expired invite rejected with the expired-specific error.
- Revoked invite rejected with the revoked-specific error.
- Invalid/malformed token rejected with the invalid-specific error,
  indistinguishable in form from any other lookup miss (§10).
- Replay: accepting the same token twice (sequentially) — second attempt
  rejected as already-used.
- Double acceptance / concurrent acceptance: two simulated concurrent
  calls with the same token — exactly one succeeds, the other gets
  "already used," never two membership rows.
- Already-a-member-of-this-household acceptance attempt — rejected (or
  short-circuited client-side, but the RPC itself must also reject it)
  with a "already a member" outcome, not a duplicate row (the existing
  `household_members_household_profile_key` unique index would also
  catch this at the database level as a backstop).
- Cross-household attack: an accept call cannot be made to create a
  membership in any household other than the one the token actually
  resolves to — there's no parameter to attempt this with in the first
  place, but the test should confirm the RPC signature truly has no such
  parameter/side channel.
- Role escalation attempt: confirm there is no way to pass or influence
  a role via this RPC; the resulting row is always `'member'`.
- Household enumeration resistance: a series of random/incorrect tokens
  against `resolve_household_invite` all produce the same generic
  "invalid" outcome, with no timing or content difference that would
  reveal whether a token was "close" to valid.

**App-level (Playwright, `--workers=1`, matching every prior slice's
fixture-safe conventions):**
- Logged-out visitor hits `/join/:token` → redirected through sign-up →
  (confirmation handled the way the existing fixture/test account
  bypasses it today) → lands back on the same invitation, accepts.
- Logged-out visitor → signs in with an existing account → same
  return-to-invitation behavior.
- **Persistent golden path**, exactly as specified: User A creates a
  household → creates an invite → User B opens the link → signs in →
  joins → User A adds a grocery shared with User B → User B refreshes →
  sees the household and the grocery → the settlement between them is
  correct (computed by the real, unmodified engine, per
  `docs/PAYMENT_PERSISTENCE_DESIGN.md`'s confirmation that the engine
  needs no changes for membership alone).

## 15. Beta impact

**What Invite/Join unlocks:** the only way, today, to add a second real
*account* to a household is to already have one before signing up at all
— there is no way for a household's owner to bring a second real person
in. This is the single hard blocker to beta: a "beta household" is by
definition more than one real person, and there is currently no way for
more than the original creator to ever get in.

**What remains after this slice ships, honestly assessed against "do not
propose optional features as blockers":**
- **Nothing else blocks starting private beta for the app's core
  purpose** (a household of real people logging real groceries and
  seeing a real, correct settlement). Real Auth, real households, real
  members (now including invited ones), real groceries, real
  history/analytics, a deterministic settlement engine, and RLS
  hardening are all already done.
- **Payment persistence** (`docs/PAYMENT_PERSISTENCE_DESIGN.md`) remains
  a known, already-designed, not-yet-built gap — "Mark as paid" still
  doesn't survive a refresh. This is a real limitation beta users should
  be told about, not a blocker to *starting* beta with the rest of the
  app fully functional.
- **Claiming an existing non-account member** (§5) stays explicitly
  deferred — a real future improvement, not required for a beta
  household's first real invite to work.
- Previously documented, pre-existing, unrelated gaps (owner-self-archive
  RLS gap, household-creator account-deletion restriction, leaked-
  password-protection's Free-plan limitation, deferred performance
  advisories) are all unchanged by this slice and were already correctly
  classified as non-blocking in their own respective audits.

## 16. Slice 8B implementation notes — deviations from this design

Slice 8B (`supabase/migrations/20260919080821_household_invites.sql`)
implemented §3/§7/§8/§10 of this design database-only, exactly as
approved, with three deviations found during implementation and adopted
there rather than silently. Recorded here per this project's practice of
keeping the design doc accurate against what actually shipped.

**1. `pgcrypto` was already installed — no `CREATE EXTENSION` statement
was added.** Re-inspecting the current database before writing the
migration (as this slice's own STEP 1 required) found `pgcrypto` already
present in the `extensions` schema, as part of Supabase's own local/hosted
project bootstrap — not something any prior GroceryMate migration
enabled. §3's assumption that this slice would need to enable it was
incorrect; the migration performs no `CREATE EXTENSION` at all. Every
call is still fully schema-qualified (`extensions.gen_random_bytes`,
`extensions.digest`) regardless, since `create_household_invite`,
`resolve_household_invite`, and `accept_household_invite` all pin
`search_path = ''` — qualification isn't optional once that's true,
whether or not the extension already existed.

**2. Re-inviting a profile with an existing archived row in the *same*
household is a real edge case §5/§8 didn't fully cover.**
`household_members_household_profile_key` — a pre-existing partial unique
index on `(household_id, profile_id) WHERE profile_id IS NOT NULL` —
means a profile that previously left a household (archived, not deleted)
and is re-invited to that *same* household cannot get a second row
inserted for that exact pairing; §8's "always insert a new row" rule
assumed a fresh pairing always succeeds. `accept_household_invite` now
catches the resulting `unique_violation` and raises a clear, specific
error ("You were previously a member of this household. Ask the
household owner to reactivate your membership.") instead of a raw
constraint message. This is not the claiming/merging feature §5
explicitly defers — it does not resurrect the archived row or link
identity, it only explains why a fresh insert failed. Re-activating an
archived membership remains future work.

**3. A second concurrency race, beyond §8's own pseudocode, was found and
closed.** §8's conditional-`UPDATE`-on-the-invite-row pattern correctly
prevents the same invite from ever being consumed twice, but a
*different* race exists: the same profile accepting two different
invites (to two different households) concurrently, each transaction
seeing "no active membership yet" before either commits — producing two
active memberships for one profile, exactly the state
`HouseholdProvider.loadHousehold` already refuses to render
(`'unsupported'`). `accept_household_invite` now takes a `select ... for
update` lock on the caller's own `profiles` row before checking for an
existing active membership, serializing any concurrent accept attempts
by the same profile regardless of which invite each one targets. This is
a correctness addition beyond this design's literal pseudocode, not a
change to intended behavior — validated under genuine concurrent
execution (two real parallel sessions, not a sequential double-call) as
part of Slice 8B's own local adversarial test pass.

No other part of §3/§7/§8/§10 required a deviation — the table's exact
column list (no `role`, no raw token, no `updated_at`), the single-use
model, the RPC surface, the authorization rules, and the security/abuse
handling all shipped as designed.

## 17. Slice 8C implementation notes — deviations from this design

Slice 8C implemented §2/§3/§6/§9/§11/§12 database-only... no, frontend-only:
routing, the invite client layer, owner link generation, `/join/:token`,
the logged-out/authenticated acceptance flows, and removal of the fake
email path. Three points are recorded here because they materially
differ from, or resolve an open question in, §6 and §12 above.

**1. No `localStorage`/`sessionStorage` breadcrumb was implemented
anywhere — the Slice 8A approval's refinement is honored exactly, not
just "by default."** §6's design offered the breadcrumb as the mechanism
the design *depended on*, with `emailRedirectTo` as a "nice-to-have"
optimization on top. The actual implementation inverts that: a
`?redirect=/join/:token` query parameter (validated against exactly one
shape — see `src/invite/routes.ts`'s `isSafeJoinRedirect`, which accepts
nothing else, making an open redirect structurally impossible rather than
merely filtered) carries the destination through the plain sign-in and
immediate-session sign-up paths, and `emailRedirectTo` — passed to
`supabase.auth.signUp()` only when the signup started from an invite —
carries it through hosted Supabase's real email-confirmation step,
because the destination is encoded in the *emailed link itself*, needing
no client-side storage of any kind, on any device. No code path in this
slice reads or writes `localStorage`/`sessionStorage` for invite state.

**2. One genuine unresolved item, exactly where §6 flagged it might
be:** whether the hosted project's Supabase Auth "Redirect URLs"
allow-list already covers `/join/*` cannot be confirmed from a local
implementation slice — dashboard Auth configuration is out of scope here
(and was out of scope for Slice 8B too). If it does not, a hosted
signup-with-confirmation-required invite acceptance would fall back to
landing on the project's default Site URL instead of the invite, though
the *account itself* would still be created correctly and the user could
still open the same invite link manually afterward and accept it — not a
security gap, only a lost convenience. This needs a hosted verification
pass (the same kind Slice 8B went through) before relying on it in
production; local verification (confirmations disabled) fully passes and
is not affected.

**3. A real concurrency-adjacent bug was found and fixed during
implementation, unrelated to the backend:** `GuestRoute` (gating
`/sign-in`/`/sign-up`) already redirects an already-authenticated visitor
away; making that redirect honor `?redirect=` too (for the edge case of
landing on sign-in already signed in) initially raced against
`SignInPage`/`SignUpPage`'s own explicit post-submit `navigate()` — both
components stay mounted for a moment during `App.tsx`'s
`AnimatePresence` exit transition, and `GuestRoute` re-rendering during
that window with the *now-changed* location (after the correct navigate
already happened) would recompute `redirect` as `null` and fire a second,
competing redirect to `/groceries`, intermittently clobbering the correct
destination. Fixed by capturing `GuestRoute`'s redirect target once, via
`useState`'s lazy initializer, rather than re-deriving it from the live
location on every render — confirmed fixed under real Playwright
execution (`tests/e2e/invite-join.spec.ts`), not just reasoned about.

No revoke button was added to the owner's UI — §3's minimum ("copyable
real URL, expiry information, clear success/error state") doesn't call
for one, and `docs/INVITE_JOIN_DESIGN.md` never asked for a pending-
invites management view. `revokeHouseholdInvite` exists in
`src/invite/inviteService.ts` and is unit-tested, ready for a future
slice if that UI is ever wanted. The fake "or send it for them" email
path (`AddMemberDialog`'s email field, `useHouseholdMembers.inviteMember`,
`useMembers.handleInvite`) was deleted outright, not merely hidden or
disabled — there is no remaining code path that can create a
`household_members` row with `status='invited'`.

## Final report

**Current fake invite behavior:** `AddMemberDialog`'s "Invite link" tab
shows one hardcoded string (`grocerymate.app/join/flat-4b`), identical
for every household, backed by no route and no server logic at all. The
same tab's separate "or send it for them" email field is a *different*,
half-real mechanism: it does write a genuine `household_members` row
(`status='invited'`), but that row can never be completed or even found
by anyone's session — a permanent orphan, not a working invite.

**Recommended MVP journey:** owner generates a real, single-use link
server-side → shares it however they like → recipient opens it, sees the
household's name, signs up or signs in if needed (returning to the exact
same invitation afterward, even across the email-confirmation gap) →
explicitly accepts → one atomic server-side transaction creates their
real, active, non-owner membership → they're in.

**Invitation model:** a new `household_invites` table — `id`,
`household_id`, `token_hash`, `created_by_member_id`, `created_at`,
`expires_at`, `revoked_at`, `accepted_at`, `accepted_by_profile_id`. No
`role`, no `use_count`, no raw token column, ever.

**Single-use/reusable decision:** single-use, with "generate invite"
kept fully repeatable so inviting several roommates is several clicks,
not a blocker — chosen over a reusable link primarily for its much
smaller abuse/leak blast radius, at negligible cost to onboarding speed.

**Token strategy:** 256-bit random token, generated server-side inside
the create-invite RPC, returned to the owner exactly once, and never
stored in plaintext — only its SHA-256 hash (`pgcrypto`, newly enabled)
is persisted and ever compared against.

**Existing non-account-member decision:** always create a brand-new
`household_members` row on acceptance; claiming/linking an existing
`profile_id=null` member is explicitly deferred — no safe automatic way
to do it exists without owner-driven, invite-time selection of a specific
target member, which is real additional scope this slice doesn't need.

**Auth redirect strategy:** the token lives in the URL; a `localStorage`
breadcrumb (not React state) survives the full signup → email-
confirmation → return gap; any transition to signed-in checks for and
consumes that breadcrumb to redirect back into the pending invite instead
of the app's normal default landing page.

**Acceptance transaction:** a single SECURITY DEFINER RPC,
`accept_household_invite(token)`, taking only the token as input; derives
the caller from `auth.uid()`; validates revoked/expired/already-used/
already-a-member-elsewhere; atomically consumes the invite (a conditional
`UPDATE ... WHERE accepted_at IS NULL`, which is also the concurrency
guarantee) and inserts the new membership row in the same function call,
so neither can happen without the other.

**Authorization/RLS model:** invite creation and revocation are
owner-only (RLS `is_household_owner`); resolution is grantable to `anon`
too, scoped to return only the household's name and the invite's
validity; acceptance is any-authenticated-user via the RPC above, never a
direct table write.

**Role/status result:** always `role='member'`, `status='active'`,
`profile_id=auth.uid()` — never `'owner'`, never `'invited'`, never a
client-influenced identity.

**Route/UI states:** one new route, `/join/:token`, outside
`HouseholdGate`; loading, valid+signed-out, valid+signed-in, accepting,
accepted, expired, revoked, invalid, already-accepted, already-a-member-
of-this-household, and belongs-to-a-different-household (reusing the
existing unsupported-multi-household messaging). No visual redesign.

**Security model:** 256-bit tokens make guessing irrelevant; single-use +
revocation + 7-day expiry bound leak/forward risk; every identity-bearing
field (`household_id`, `role`, `profile_id`) is server-derived, never a
client parameter; a conditional atomic UPDATE closes the double-
click/concurrent-acceptance race; resolution responses are uniform enough
that no household can be enumerated by probing tokens.

**Test strategy:** full RLS/RPC adversarial matrix (owner-only creation,
anon resolution scope, impersonation/escalation attempts, replay,
concurrency, cross-household attempts, enumeration resistance) plus
Playwright coverage of the real redirect-through-auth journeys and one
persistent golden-path E2E (two real users, a real invite, a real
grocery, a real correct settlement).

**Migration sequence:** 8B (schema/RLS/RPCs only) → 8C (frontend
Invite/Join, including removing the old fake link and the old orphaned
email-invite UI) → 8D (hosted golden-path verification) — tested locally
end to end before either touches hosted, same discipline as every prior
slice.

**Remaining blockers to private beta:** none, once this slice ships —
this was the one hard blocker (no way to bring a second real person into
a household at all). Payment persistence, non-account-member claiming,
and the several previously-documented pre-existing gaps all remain
correctly classified as non-blocking, already-communicated limitations,
not blockers to starting beta.

**Estimated implementation complexity: MEDIUM.** Not SMALL — a new
table, a new extension, three RPCs (one of them a real atomic
transaction with a genuine concurrency guarantee to get right), a new
top-level route with real cross-auth-flow state handling, and a
meaningful adversarial test surface. Not LARGE — no new UI design system
work, no email infrastructure, no multi-household support, no claiming
logic, and every hard architectural question (token storage, RLS shape,
atomicity pattern) has a direct, already-proven precedent elsewhere in
this codebase to follow rather than invent from scratch.
